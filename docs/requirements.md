# Требования

## Цель и границы

При задержке или отмене рейса участник должен понять последствия для поездки, получить сохраняемое уведомление и выбрать допустимое изменение общего плана

В область Alfred входят статусы, расчёт последствий, уведомления, подбор альтернатив и версии плана. Поиск и фактическое изменение бронирований выполняются модулями TravelTech и поставщиками за границей Alfred

Допущения:

- Все участники одной поездки следуют общему плану; автоматическое разделение группы не предусмотрено
- Багаж и разрешения на маршрут заданы для каждого участника отдельно
- Организатор подтверждает изменения или делегирует это право участнику
- TravelTech предоставляет расписания, условия бронирований, MCT и проверку права на маршрут с указанием основания и срока актуальности
- Если сведения отсутствуют, система показывает неопределённость и не объявляет вариант допустимым
- Общий план может содержать выбранные, но ещё не забронированные элементы; их статус виден участникам

MCT (Minimum Connection Time) означает минимально допустимое время пересадки для конкретных условий. Значение зависит от аэропорта, терминалов, перевозчиков и типа пересадки; универсального MCT нет

## Участники

| Участник | Права |
|---|---|
| Организатор | Просмотр поездки, изменение ограничений, делегирование и подтверждение |
| Участник | Просмотр своей поездки, уведомлений и альтернатив; подтверждение при `can_confirm=true` |
| Поставщик статуса | Передача статусов своего потока без доступа к поездкам |
| Оператор поддержки | Диагностика и повтор обработки; без права менять планы и без паспортных данных |

## Функциональные требования

| ID | Требование |
|---|---|
| F-01 | Сопоставлять событие по полному ключу рейса; неизвестный рейс сохранять как `unmatched` |
| F-02 | Принимать повторы без повторных последствий; одинаковый ID с другим содержимым считать конфликтом |
| F-03 | Применять только актуальное подтверждённое состояние; при спорных данных сверяться с назначенным источником |
| F-04 | Рассчитывать последствия для всех элементов общего плана, связанных с изменившимся рейсом |
| F-05 | Сохранять персональное уведомление каждому участнику независимо от доступности устройства и push/email |
| F-06 | При нарушении плана автоматически запрашивать альтернативные перелёты или активности |
| F-07 | Проверять багаж, право на маршрут, места всей группе, пересадки, географию, время и срок предложения до ранжирования |
| F-08 | Перед подтверждением повторно проверять условия предложения, права и версии плана и состояния рейса |
| F-09 | Атомарно сохранять новую версию плана, уведомления и результат запроса; повтор не создаёт версию |
| F-10 | Проверять членство в поездке на каждом пользовательском запросе; одного знания `trip_id` недостаточно |
| F-11 | Показывать недоступность источника, время последней проверки и причины отсутствия допустимых вариантов |
| F-12 | Для отеля и трансфера создавать `booking_action_required`, если требуется уточнение или изменение брони |

## Правила расчёта

- Пересадка допустима, если вылет следующего рейса минус ожидаемое прибытие не меньше `MCT + buffer`; равенство допустимо. Для смены аэропорта отдельно учитывается переезд
- Достижимость отеля, трансфера или активности определяется ожидаемым прибытием, выходом из аэропорта, переездом, запасом и крайним допустимым временем
- При отмене рейса фактическое прибытие не придумывается; зависимые элементы требуют восстановления транспортного участка
- При неизвестных временах или правилах создаётся последствие `needs_information`; неподтверждённая достижимость не считается безопасной
- Позднее прибытие само по себе не означает отмену отеля. Нужны условия конкретной брони
- Активность может заменить другую активность или заполнить ожидание, но не заменяет необходимый перелёт
- Вариант должен подходить каждому участнику; неизвестное или истёкшее разрешение на маршрут исключает вариант
- Перелёты ранжируются по общему времени в пути, числу затрагиваемых элементов, цене и ID; активности по соответствию интересам, затем цене и ID. Цена сравнивается в валюте поездки, без неявной конвертации
- Изменение участников, ограничений или состава плана создаёт новую версию; обновление оперативного статуса рейса меняет его `state_version`

## Нефункциональные требования

| ID | Требование и проверяемая цель |
|---|---|
| N-01 | После ответа о приёме событие сохранено; сбой обработчика допускает повтор без потери и дублирования результата |
| N-02 | Все сравнения времени выполняются в UTC; отображение использует IANA-зону каждого места, включая переходы летнего времени |
| N-03 | Паспортные поля запрещены в запросах, хранилище и логах Alfred; тело ошибочного запроса не логируется |
| N-04 | Только HTTPS; пользователь определяется проверенным токеном TravelTech, сервисный отправитель отдельной служебной учётной записью |
| N-05 | Цель: p95 от приёма подтверждённого статуса до сохранения уведомления не более 5 с при 10 событиях/с; проверка на 1000 событиях после прогрева |

Числа N-05 являются проектной целью, измерений реализации нет. Задержка самого источника измеряется отдельно и не скрывается в этом показателе

Паспортные данные, необходимые для бронирования, остаются в защищённом модуле TravelTech. Он отвечает за удаление, когда цель обработки завершена и нет иного обязательного основания хранения; срок не продлевается для рекомендаций. В Alfred передаются только непрозрачная ссылка на бронь и результат проверки допустимости маршрута
