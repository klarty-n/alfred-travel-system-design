# Интеграции и контракты

## Общий подбор TravelTech

Обычный поиск и Alfred используют один модуль подбора

| Контракт | Вход | Выход / ответственность |
|---|---|---|
| Search.candidates | SearchCriteria, cursor | CandidatePage: нормализованные предложения, checked_at, next_cursor, состояние источников |
| Offers.revalidate | provider_offer_id, fingerprint, актуальные критерии | Полные текущие условия, доступность, checked_at/expiry; changed/expired/unavailable |

Общие правила подбора:

- Проверка предложения: багаж, места, право на маршрут, статус, срок и валюта
- Проверка маршрута: достижимость стыковок и временных окон по текущему плану или проекту замены
- Ранжирование допустимых вариантов по выбранной политике с объяснением порядка

SearchCriteria содержит вид flight/activity/hotel, маршрут/место, UTC-окно с earliest_start_at, группу, требования каждого участника, интересы и валюту. Обычный поиск формирует его из формы, Alfred из плана и последствия. Паспортные данные и произвольный доступ к БД Alfred общему модулю не передаются

Обработка типов различается внутри общих правил: отелю нужны гости и заезд, перелёту багаж и пересадки, активности вместимость/место/время. Alfred в этой границе запрашивает flight/activity; hotel остаётся функцией обычного TravelTech

Версия общих правил обозначается rules_version. Обычный поиск использует DISCOVERY и пользовательские критерии; Alfred использует RECOVERY_FLIGHT или RECOVERY_ACTIVITY. Политику восстановления определяет Alfred, общий код проверок и сортировки не копируется. Длительность восстановления считается от общего earliest_start_at до прибытия; interest_score равен сумме пересечений тегов активности с интересами каждого активного участника, при пустых интересах 0

За границу TravelTech передаются только необходимые параметры поиска: маршрут, даты, агрегированные требования и размер группы. Имена, внутренние user_id/trip_id, документы и история путешествий поставщикам поиска не передаются; решения по разрешениям проверяются в доверенном контуре

Адаптеры выполняют аутентификацию у поставщика, запросы и перевод форматов. Они не определяют, какой вариант лучше восстанавливает поездку. Входящие ограничения проверяются до лимитирования выдачи, если поставщик поддерживает их корректную семантику; фильтр включённого багажа не должен скрывать тарифы с подходящей платной опцией

CandidatePage возвращает next_cursor и сведения о незавершённых/недоступных источниках. Alfred обрабатывает следующие страницы до завершения поиска или явно показывает search_complete=false. Пустая первая страница не означает none_eligible; частичный список не объявляется лучшим на всём рынке

Кандидат идентифицируется поставщиком, provider_offer_id и fingerprint условий. Номер рейса не заменяет ID тарифа. Для перелёта нужны полные условия каждого участка и участника. В API baggage_by_member передаёт индивидуальные нормы, baggage_kg является их минимумом; проверка MCT учитывает терминалы/тип пересадки и переезды. Отсутствие данных исключает подтверждённую допустимость

Цена является полной стоимостью нового предложения для всей группы в минимальных единицах одной валюты: сборы и выбранный допбагаж включены. Неизвестные штрафы и возвраты прежних броней не вычитаются и показываются как отдельные действия

Разрешение на маршрут содержит маршрут/дату применения, результат allowed/denied/unknown, основание и valid_until проверки. Истечение проверки или неприменимость к датам поездки требуют нового подтверждения у доверенного TravelTech. Сами документы Alfred не получает

## Статусы и контекст

| Контракт TravelTech | Запрос | Ответ |
|---|---|---|
| Status.current | Полный FlightKey, назначенный источник | Состояние, времена, поток/ревизия, время наблюдения/проверки и основание достоверности |
| Booking.tracked_trips | Служебная учётная запись, cursor | Начальная загрузка активных поездок, затем изменения/отключения, source_revision, next_cursor и has_more |
| Booking.context | trip_id, source_revision, служебная учётная запись | Исходный план с местами и временными окнами, участники/права, tracking_enabled, факты конкретных услуг брони, ограничения/интересы и временные правила |

Конкретные внешние API выбираются при интеграции. Монотонная source_revision контекста относится к одной поездке; received_at её не заменяет. Одинаковая ревизия требует одного нормализованного содержимого, противоречие уходит на сверку

После подключения Alfred владеет согласованным планом, Booking фактическими бронями. Booking.action_result обновляет контекст источника; Alfred получает подтверждение при синхронизации, сопоставляет booking_ref с актуальным элементом и не восстанавливает старую заменённую бронь

Поставщик статуса вызывает адаптер webhook, адаптер передаёт StatusEvent в служебный HTTP-вход Alfred. Опрос использует тот же приём и проверку. При наличии надёжной версии снимка ID опросного события строится из неё; иначе из ID устойчивой задачи опроса и хеша ответа. Цикл опроса не доказывает новизну состояния

## HTTP API Alfred

Точный контракт находится в [OpenAPI](../api/openapi.yaml)

| Метод | Назначение |
|---|---|
| POST /internal/flight-status-events | Сохранить событие и задачу обработки |
| GET /trips/{trip_id} | Получить текущий план, состояния, последствия и свежесть контекста |
| GET /trips/{trip_id}/inbox | Собственные сообщения участника, cursor/limit |
| GET /trips/{trip_id}/impacts/{impact_id}/alternatives | Актуальные сохранённые варианты и полнота поиска |
| POST /trips/{trip_id}/selections | Подтвердить offer с expected_plan_version и Idempotency-Key |

Каждый запуск имеет SearchRun с состоянием/cursor, признаками источников и причинами исключения. Impact указывает текущий search_id. Одна задача OutboxTask с этим search_id возобновляется для следующих страниц. Offer, SearchRun и переход этой задачи в ready/done фиксируются атомарно при актуальных версиях и lease. Новый запуск заменяет указатель; поздние ответы старого не публикуются

GET alternatives читает текущий SearchRun и его Offer, включая пустую выдачу. Новый запрос к поставщикам при открытии экрана не выполняется. available содержит проверенные варианты; search_complete=false предупреждает о неполноте. searching и temporarily_unavailable имеют пустой список, none_eligible требует search_complete=true. Истёкшие варианты не возвращаются как доступные. Недостаточные критерии дают temporarily_unavailable с объяснением needs_information; после обновления контекста создаётся новый SearchRun

Пользователь определяется проверенным Bearer-токеном: подпись, issuer, audience, exp, затем active и членство. Владение UUID не даёт доступа. Статусы используют отдельную служебную audience с привязкой provider_id; оператор имеет отдельный служебный доступ к диагностике/повтору, без изменения плана

| Ответ | Значение |
|---|---|
| 200 | Чтение, сохранённый выбор или точный повтор события |
| 202 | Event и задача надёжно сохранены |
| 401 | Токен отсутствует или недействителен |
| 403 | Нет права подтверждения либо provider_id не соответствует служебному токену |
| 404 | Объект отсутствует или относится к чужой поездке |
| 409 | Конфликт версии/ключа, устаревший вариант, изменённые/истёкшие условия |
| 422 | Нарушение закрытого контракта или бизнес-валидации |
| 503 | Хранилище или обязательная повторная проверка недоступны |

Idempotency-Key ограничен trip+actor+operation. Доступ проверяется до выдачи прежнего успешного результата. Тот же ключ с другим каноническим телом даёт 409; успешный повтор не создаёт версию и не зависит от последующего expiry исходного offer

Inbox упорядочен по sequence_no, назначенному под блокировкой Trip. Cursor привязан к trip/user, created_at и UUID не используются как гарантия порядка commit

Моменты передаются ISO 8601 UTC с Z, зоны IANA и исходные локальные даты/время сохраняются отдельно. Деньги являются целым числом минимальных единиц + ISO 4217, аэропорты IATA-кодами. Неизвестные входные поля, паспорта и секреты не сохраняются в payload или логах
