# Пример: задержка и новая версия плана

Все рейсы, цены, MCT и ограничения в примере вымышлены и служат для проверки логики

## Исходный план

Поездка T-1, версия 1, три участника. Анна организатор, Борис и Вера участники без права подтверждения. Требуемый багаж: 23, 23 и 10 кг. Все элементы плана общие. T-1 и названия участников являются обозначениями примера, в API используются UUID

Дата вылета: 12 ноября 2026 года

| Элемент | Местное время | UTC |
|---|---|---|
| AX 101, LAX → SFO | 14:30 → 16:00, America/Los_Angeles | 22:30 → 00:00 следующего дня |
| AX 202, SFO → SEA | 17:10 → 19:10, America/Los_Angeles | 01:10 → 03:10 следующего дня |
| Трансфер SEA → отель | Последний выезд 20:00, America/Los_Angeles | 04:00 следующего дня |
| Отель в Сиэтле | Крайний check-in 22:00, America/Los_Angeles | 06:00 следующего дня |
| Прогулка в Сиэтле | 13 ноября, 10:00, America/Los_Angeles | 18:00 |

AX обозначает выполняющего перевозчика, 101 является номером рейса. Обозначения и расписание заданы для этого примера

Для пересадки заданы учебные MCT 45 минут и запас 15 минут. Исходный интервал 70 минут, требование 60 минут выполнено

## Событие

Назначенный поставщик `demo-status`, поток `stream-1`, прислал событие `evt-42` с ревизией 8 вместо сохранённой 7. Ключ AX/101/2026-11-12/LAX/SFO/14:30 однозначно сопоставлен

Ожидаемое прибытие в SFO теперь 16:40, то есть 00:40Z 13 ноября. Событие пришло через 10 минут после наблюдения; это отображается как задержка источника. Новое значение принимается по ревизии, а не по времени доставки

До AX 202 остаётся 30 минут, требуется 60. Alfred сохраняет последствие «пересадка недостижима» и по одному уведомлению Анне, Борису и Вере. Борис оффлайн, его сообщение остаётся в inbox

Достижимость элементов после AX 202 не объявляется гарантированной. Трансфер и отель требуют повторного расчёта после выбора нового перелёта

## Автоматический подбор

Alfred сформировал SearchCriteria по текущему плану, создал SearchRun и запросил кандидатов через общий модуль TravelTech. Курсор и состояние выдачи сохраняются в SearchRun; следующую страницу обрабатывает та же возобновляемая задача. Общие правила проверяют предложения для всей группы и стыковки в проекте замены. Допустимые варианты ранжируются по RECOVERY_FLIGHT. Обычный поиск использует те же правила с другой политикой

В рассматриваемой выдаче получены следующие учебные варианты

| Вариант | Проверка | Результат |
|---|---|---|
| SFO → SEA, включено 15 кг | Нужно 23 кг, возможность/стоимость доплаты не подтверждены | Не включён в подтверждённо допустимые; требуется проверка опций |
| SFO → SEA, багаж 23 кг, 2 места | В группе 3 человека | Отклонён |
| Перелёт с международным транзитом | У Веры неизвестно разрешение на транзит | Отклонён |
| AX 204 SFO → SEA, 18:30 → 20:30, 23 кг, 3 места | Пересадка 110 минут, разрешения актуальны | Допустим для замены перелёта, остаются действия по трансферу |

Если поставщик подтвердит норму не менее 23 кг с платной опцией, первый вариант проверяется заново с полной ценой для группы. Неподтверждённая доплата не предполагается. Отсутствие подходящего кандидата на первой странице не завершает поиск: Alfred использует next_cursor и показывает search_complete

Для AX 204 выход из аэропорта 30 минут, запас 15 минут. Готовность к трансферу в 21:15 позже 20:00: требуется изменение трансфера. При согласованном новом трансфере с дорогой 45 минут прибытие к отелю в 22:00 укладывается ровно в крайнее время, но результат зависит от подтверждения трансфера

Alfred показывает `booking_action_required` для трансфера. Время 22:00 само по себе не нарушает заданное окно отеля, но достижимость зависит от ещё не подтверждённого трансфера; условия заезда требуется уточнить. Утреннюю прогулку можно сохранить, если новые условия поездки подтверждены

Если задержка сделала бы прогулку недостижимой, система автоматически запросила бы другую активность с подходящими местом, временем и вместимостью. Такая активность не заменяет AX 202

## Подтверждение

Анна выбирает сохранённый offer для AX 204 с `expected_plan_version=1` и ключом `selection-01`. Alfred получает актуальные условия через Offers.revalidate и повторяет общие проверки предложения и маршрута для всех участников. Цена, багаж, места и разрешения не изменились

В короткой транзакции система повторно проверяет права, версию 1 и исходные состояния рейсов. Создаётся версия 2, элемент AX 202 становится архивным с `is_current=false`, новый элемент AX 204 получает другой ID и `needs_booking`; изменение трансфера остаётся отдельным действием. Старая бронь AX 202 автоматически не отменяется

История версии 1 сохраняется. Пересчёт версии 2 имеет другой ключ задачи, даже если исходный Flight.state_version не изменился. Всем участникам записывается уведомление об изменении плана; Борис увидит версию 2 и сообщения при возвращении в сеть

Повтор запроса с `selection-01` возвращает сохранённую версию 2. Одновременное другое подтверждение с ожидаемой версией 1 получает 409. Если за время повторной проверки изменился рейс, подтверждение также отклоняется и альтернативы рассчитываются заново

При оформлении AX 204 TravelTech получает ID поездки и нового элемента плана. После подтверждения билета факт появится в Booking.context. Alfred привяжет booking_ref к текущему элементу AX 204 и отметит его booked в версии 3. Если к этому моменту элемент уже заменили, подтверждение не меняет текущий план
